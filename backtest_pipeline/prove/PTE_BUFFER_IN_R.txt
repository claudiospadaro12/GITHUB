# LA TESI, scritta PRIMA dei numeri
#
#   R67 ha trovato che nella PTE il target e' in ATR puro e lo stop e'
#   ATR + buffer (ABTG_PTE.mq5:329-330 e :338):
#       tp   = entry +- atr * InpTP2_ATRmult      <- SOLO ATR
#       risk = atr   +  InpSLbufferPips * pip     <- ATR + buffer
#   quindi        R_target = (ATR * TP2mult) / (ATR + buffer)
#
#   👉 **`InpSLbufferPips` NON e' un parametro dello stop: e' una manopola
#      sul TARGET IN R, e nessuno lo sapeva.** Muovendo il buffer si sposta
#      il target senza accorgersene.
#
#   LA DOMANDA DI QUESTO ROUND, in una riga:
#      **una volta tolto l'effetto sul target, il buffer conta ancora?**
#      Cioe': il buffer serve a qualcosa DI SUO (protegge lo stop dal
#      rumore) oppure e' solo un modo storto di scrivere l'R?
#
# ---------------------------------------------------------------------
# 🔑 LA SCORCIATOIA CHE RENDE IL ROUND POSSIBILE SENZA CODICE
#
#   Per tenere R costante servirebbe l'ATR tipico di GBPUSD H1, che NON e'
#   misurato. Ma non serve, perche':
#
#      con **buffer = 0**  ->  risk = ATR  ->  **R_target = TP2mult ESATTO**
#
#   La riga `buffer 0` e' quindi il RIFERIMENTO IN R PURO: li' il target
#   in R e' esattamente il numero che scriviamo, senza dipendere dall'ATR.
#   Tutte le altre righe hanno lo stesso target in PREZZO ma un R piu'
#   basso, tanto piu' basso quanto e' grande il buffer.
#
#   ⚠️ buffer 0 e' legale: `sl = entry-(atr+0)` -> risk = ATR, sempre
#   positivo e ordini di grandezza sopra lo STOPS_LEVEL. Il controllo di
#   riga 335 non scatta.
#
# ---------------------------------------------------------------------
# COME SI LEGGE (deciso ORA, prima dei numeri)
#
#   1. **La riga buffer=0 e' la baseline.** Si guarda la sua curva su
#      TP2mult: e' la vera curva "profitto contro R", pulita.
#   2. **Poi si confrontano le righe a buffer crescente.** Due esiti:
#      A) le righe col buffer sono spiegate dallo SPOSTAMENTO DI R
#         (cioe' buffer 10 a TP2mult X somiglia a buffer 0 a un TP2mult
#         piu' basso) -> **il buffer non ha vita propria: e' l'R.
#         La PTE ha un parametro in piu' che non serve.**
#      B) le righe col buffer stanno SISTEMATICAMENTE sopra (o sotto) la
#         baseline a parita' di R -> **il buffer fa qualcosa di suo**
#         (probabilmente protegge lo stop dal rumore) e va tenuto, ma
#         allora va tarato SAPENDO che muove anche il target.
#   3. 🔴 In nessuno dei due casi si cambia qualcosa in forward con questo
#      round: e' OHLC. Il verdetto e' a tick reali, e la PTE e' una sedia
#      viva (unico motore positivo in tutti e 4 i regimi di R50).
#
# ---------------------------------------------------------------------
